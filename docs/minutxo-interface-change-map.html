Two script-facing capabilities changed

Comparison baseline: “Before this interface patch” means the state of minutxo-incremental after Nicolas’ minUTxO changes and the earlier integration work, but before this interface patch. It does not mean Cardano before the minUTxO proposal or the interface of deployed validators.

Changed default

Read total value consistently

Before this interface patch
The default view omitted separately allocated backing for explicit outputs.
After this interface patch
The default includes that backing, so it represents total value for either output kind.
Why
A validator checking an ADA payment can use one rule without inspecting the output’s representation.
New information

Inspect explicit backing

Before this interface patch
The script-facing output did not report the separate allocation.
After this interface patch
Optional metadata identifies implicit versus explicit backing and reports the actual explicit amount.
Why
A contract that cares about that allocation can check it directly instead of trying to infer it from the total.
Preserved as an option

Read value excluding explicit backing

The old default already provided this view. Once the default becomes total value, a helper preserves the previous view for contracts whose accounting intentionally excludes separate backing.

This is a retained capability, not a newly possible calculation. Token quantities are identical in both views; simply checking a token quantity does not require the helper.

Implicit outputs: there is no separately recorded split to expose. Their full value is preserved by the helper. The interface does not infer which ADA the application considers payment or infrastructure.

What had to support those capabilities?

Correct information

Supply backing facts to context construction

For an existing output, use its recorded allocation. For a new output, use the allocation it is required to receive.

Why: recomputing an old allocation using today’s prices could produce the wrong total. Missing or invalid metadata must fail instead of becoming a guessed amount.

Consistent evaluation

Provide those facts wherever scripts are evaluated

Both node validation and local transaction-building tools need enough information to construct the updated view.

Why: checking a script locally must use the same meaning of value as checking it on the node. This is why data had to pass through existing callers.

These are enabling requirements for the two interface capabilities, rather than additional business use cases. The implementation’s supported paths and remaining limitations are recorded in the detailed view.

Why was the code change larger than that?

Core change

Define and populate the new view

Change the script-facing types and the ledger’s mapping into those types.

Supporting integration

Make the required facts available

Update callers and local evaluation paths so the view can be constructed correctly.

Build prerequisites / evidence

Compile and verify the wider stack

Package imports, old fixture repairs, wallet dependency repairs and test-harness work added volume. They did not add further interface capabilities.

What this work does not add

  • A new minUTxO calculation, storage layout or ledger accounting rule.
  • Backwards compatibility for existing validators, or a new Plutus execution engine.
  • A recorded backing split for implicit outputs, or automatic knowledge of an application’s payment intent.
  • Wallet Dijkstra transaction writing or standalone store-backed coin selection.
How does the implicit-backing alternative fit?

The abstract goal—access to total value and another useful view—does not dictate where ADA is stored. But an additional view requires a well-defined amount to exclude.

The current implementation uses recorded explicit allocations. An alternative could expose an implicit output’s calculated minimum, but that is a different quantity with different semantics. That alternative is not implemented or audited by this report.
